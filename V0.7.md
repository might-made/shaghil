# SHAGHIL V0.7 — Creative Production System

Starting point: locked V0.6 `6a1064958930a1b8bec04a60de6344e0c1f75bff`. Work belongs only to `shaghil-v0.7`; no merge or Production promotion. V0.6 remains locked. Version: `0.7.0`.

## Milestone 1 — Product Library and Content cards

Products are separate from brand logo/reference assets. IndexedDB upgrades the existing database without replacing Brand Brain or visual history. Up to 12 products retain original PNG/JPEG/WebP Blobs (8MB maximum, 40 megapixel decode limit), a lightweight reference copy, name, description and exact/creative preference. Exact is the default. Editing/deleting library entries does not rewrite saved creatives.

Content items render as cards with a summary, full details and a direct design action; the exact source excerpt becomes the primary idea, with the entire result retained as secondary context. Unstructured results retain the previous fallback. Campaign/Offer and all six engines remain available.

Assets remain local to this browser and origin. Different Preview URLs do not share IndexedDB/localStorage. Clearing browser storage removes data. No cloud storage, vendor or dependency was added. Large images never enter localStorage.

Validation: complete `npm run qa` (V0.5, V0.6, M1) passes with simulated responses; no live generation.

## Milestone 2 — Product fidelity and controlled composition

Studio selects a saved product and defaults to its fidelity preference. Exact Product sends product metadata and a scene-only instruction; neither the original product pixels nor brand reference images go to the image model in this mode. The unmodified original product Blob is preserved in the creative snapshot and drawn by canvas over the separately generated background. Size, horizontal/vertical placement, logo visibility and local text edits reuse that background without an API request. Logo proportions and programmatic Arabic text remain intact.

Creative Product sends the lightweight product reference plus brand references to the image edit endpoint and explicitly permits interpretation. Its product pixels are part of the generated background; local product-layer positioning applies only to Exact Product.

No automatic background removal, relighting, perspective matching, realistic shadows or photorealistic integration is implemented. Opaque JPEG/PNG uploads retain their rectangular background; transparent PNG is recommended. Canvas scaling resamples pixels for the final output but does not generatively redraw the product. AI backgrounds can still contain unwanted objects and must be reviewed. Composition failures visibly warn that only a background was saved.

Validation: V0.5/V0.6/M1/M2 suites pass, including original Blob identity in compositor draws, preserved proportions, 27 format/size/horizontal-position combinations, original logo, separate scene, exact raster exclusion, Creative reference forwarding and zero new requests for local controls. No live image generation.

## Milestone 3 — Light editor and explicit variations

Local headline/CTA, top/bottom text panel, logo visibility/corner, product size/position and fit-resize controls reuse the saved background. Canvas reserves space so product/logo layers do not sit under the text panel. Local resize fits with brand-color padding; it does not crop the original product.

A separate paid-action area offers one explicit new background, one selected variation (Product Hero, Lifestyle, Performance Ad, Minimal Premium, Editorial), or one AI recomposition for 1:1/4:5/9:16. Existing second-version/Premium/Minimal actions remain. In-flight locking covers both action areas. Each new creative keeps a parent/root relationship and snapshots its product, business, brand, copy and source context.

Background-only replacement is supported for Exact Product or no-product scenes. It is blocked with a clear explanation for Creative Product because those interpreted product pixels are fused with the generated background. Return to Studio and choose Exact Product to separate those layers. No automatic segmentation is implied.

Validation: all prior suites plus M3 pass. Editor changes make zero API calls; background, variation, second version and AI recompose each make exactly one mocked request. Concurrent clicks are ignored, source/product/copy remain attached and history reopens. No live generation.

## Milestone 4 — Campaign packs and export

Campaign packs group approved creative snapshots under the business/project and campaign, with individual idea, format, caption and CTA. Each saved entry is independent of subsequent edits and the ten-item recent-history limit. Existing IndexedDB upgrades to version 3 with a packs store; V0.6 brand and visual Blobs are preserved. Limits are six packs and twelve approved entries per pack.

Export creates a local, dependency-free UTF-8 ZIP containing rendered images, approved copy/CTA text files and a manifest. The export is capped at 150MB and makes no model or network requests. There is no new database service, cloud storage, paid service or dependency. Saving is disabled while generation/composition or pack selection loading is in progress.

## Post-M4 fix — Product Library upload UX

Founder Live QA found that selecting a real product image decoded correctly and saved correctly, but the file input's native "no file chosen" reset immediately after selection, and no pending-image preview was shown before Save, making a working upload look failed.

Fix: the pending image and its status text are no longer cleared on a successful decode (only an actual validation error, a replacement selection, `Products.reset()`, or a completed save now clear them). A preview thumbnail (`#productPreviewWrap`/`#productPreview`) renders immediately after decode, and the status text explicitly names the required next action, `حفظ المنتج / Save Product`. Editing an existing library entry also now shows its saved image in the same preview.

Added `scripts/qa-v07-upload-ux.mjs` (wired into `npm run qa`) exercising `Products.upload`/`save` directly against real DOM elements and `fake-indexeddb`: preview visibility across success/error/replacement/save, the bilingual save prompt, refusal to save without a pending image, and thumbnail persistence after a simulated reload. This closes a prior automation gap — file-picker interaction was previously only covered by manual Chrome QA outside the repository.

No M1–M4 behavior, storage schema, or API surface changed. No live image generation was used.

## Post-M4 fix — Product Library persistence after Save & Start / Business Brain re-entry

Founder Live QA reported a second Product Library defect on the deployed preview: two products with images saved and survived one browser refresh, but after a blocked "Save & Start" (Business Brain fields incomplete) and reopening Business Brain, one saved product ("Wash Me") disappeared from the library while the other remained; re-adding it did not restore it.

Investigation: `saveProduct`/`listProducts`/`deleteProduct` in `lib/visual-storage.mjs` were confirmed to write and delete products individually by id — there is no code path that replaces or bulk-overwrites the product array, and the reported sequence (validation-blocked `saveProject()`, then `setup()`/`Products.refresh()` on Business Brain re-entry) was reproduced step-for-step against a real DOM harness without finding an id collision, a race, or a store-wipe. The one asymmetry found: Product Library is the only place in the app that persists a raw `File` object straight from the `<input>` element (to keep the "Exact Product" pixels untouched), while every other asset (Brand Brain logo/references) is already re-encoded into an owned `Blob` before being saved. Persisting a live `File` tied to an input's selection is a known-fragile pattern in browser IndexedDB implementations — the input is reset immediately after every save (`Products.reset()`), and that is exactly the kind of later DOM mutation on the source input documented to invalidate such a reference in some browsers, well after the initial save+immediate-reload had already succeeded.

Fix (`lib/product-library.mjs`): `Products.upload()` now copies the selected file into a plain, memory-owned `Blob` (`new Blob([file], {type: file.type})`) before it ever becomes the pending/saved image — byte-identical, so "Exact Product" fidelity is unaffected, but fully detached from the input element's lifecycle. `Products.refresh()` also now renders each saved product independently: if any single stored record ever fails to render (whatever the cause), it shows as a degraded placeholder card with a delete action instead of silently erasing the *other*, healthy products from the visible list — closing the "one bad record hides its siblings" blast radius regardless of trigger.

Added `scripts/qa-v07-product-persistence.mjs` (wired into `npm run qa`, run as its own process for a clean IndexedDB): drives the real `setup()`/`saveProject()`/`Products` code together, saving two real products with images, then replays the exact reported sequence — browser refresh, a validation-blocked Save & Start, reopening Business Brain, and a second reload — asserting both products are still listed, still render, and their exact original image bytes are unchanged throughout.

This could not be reproduced as a live browser storage fault in this non-browser test environment (jsdom/fake-indexeddb cannot model a real browser's file-handle lifecycle), so the fix targets the one confirmed, well-documented fragility in the code rather than a directly reproduced crash. No M1–M4 behavior, storage schema, or API surface changed; no live image generation was used.
