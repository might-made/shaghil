# SHAGHIL V0.8 — Complete the workflow

Starting point: Founder-QA-passed V0.7 `16dfe7b6b388f2996f3b19bf0dda05fd9a5fb51d` (FUNCTIONAL MVP — FOUNDER QA PASSED). Work belongs only to `shaghil-v0.8`; no merge or Production promotion. `shaghil-v0.7` remains as closed/frozen as `shaghil-v0.6`. Version: `0.8.0`.

V0.8's single product objective: complete the workflow the six engines already run inside — Business Brain → choose engine → generate → refine → save → history → reopen/reuse — without adding a seventh engine, redesigning the product, or building speculative infrastructure.

## A — Result persistence

Every generated result already carried `engine`, `inputs` and `text`. It was missing which business/project it belonged to, which matters once a Founder switches Business Brain between projects: an old saved result had no way to say which business it was generated for. A saved entry now also records `project` (the Business Brain name at save time) and a stable `id` (`crypto.randomUUID()`), alongside the existing `ts`. Storage stays the existing local-first `localStorage['shaghilHistory']` array — no cloud persistence, no new dependency, no new storage layer. A relevant product reference already exists for the separate Visual Studio flow (each saved visual record already snapshots its `product`); the six text engines have no product concept of their own, so there is nothing further to attach there.

## B/C — History and explicit Save UX

Before V0.8, every generation was silently auto-saved into a rolling 10-item log with no user action and no delete — ambiguous by the Founder's own description. This is now explicit:

- The result screen (`#output`) has a **حفظ في السجل / Save to History** button and a status line that always says whether the current result is saved (`تم الحفظ في السجل ✓`) or not (`لم يُحفظ بعد — اضغط "حفظ في السجل"...`). Nothing is saved until the Founder clicks it.
- A brand-new generation, a refinement, or a second version are each a new, unsaved result — the button re-enables and the status reverts, so a refined result needs its own explicit save (no invisible overwrite of what was already saved, no over-built version control).
- Reopening a saved result from history marks it as already saved (button disabled) since it *is* the saved copy; regenerating from there produces a new, unsaved result again.
- `السجل` now shows each saved result's project name alongside its engine/type and timestamp, and every entry has a **حذف** (delete) action, confirmed before removal.
- The cap moved from 10 (silently pruning the oldest on every single generation) to 30 explicitly-saved entries, so what gets pruned is only ever something the Founder chose to keep, and far less often.
- Older, pre-V0.8 history entries (no `project`/`id`) continue to open, refine and copy exactly as before — nothing already saved is lost or migrated.

## D — Reuse

Reopening a saved result (`openHistory`) still renders it without any regeneration or API call — unchanged from V0.7. From there, refine/second-version/copy all work exactly as they did, now simply producing a new unsaved result that itself can be saved. No versioning, diffing or linking between a saved result and its refinements was added, per the explicit instruction not to over-engineer this.

## E — Grounding

Already strengthened as part of the V0.7 closeout commit this branch starts from (shared `BASE` prompt in `api/generate.mjs`, applying to all six engines: no invented product/business facts, creative language kept visibly separate from factual claims, gender-neutral Arabic by default; `whatsapp` additionally told to acknowledge a missing product detail rather than invent one). V0.8 makes no further change here — it is inherited, not re-implemented, and its regression coverage (each engine's `instructions` asserted to include the grounding directives) carries forward unchanged.

## F — Visual execution architecture (inspection only, no new code)

Inspected the existing Visual Studio pipeline (`lib/visual-studio.mjs`'s `payload()`/`generate()`, `api/visual.mjs`) to find the smallest safe path for Business Brain (logo, brand references, colors, visual direction) and Product Library (exact product images, names, descriptions) to become real generation inputs, per the brief.

**Finding: that path already exists and already shipped in V0.7 M1–M4, Founder-QA-passed.** `payload()` already sends the brand's logo and reference images (base64) plus its colors/style, and the selected product's name/description/fidelity to `/api/visual` on every generation; in Exact Product fidelity the original product photo is composited locally by canvas over the generated background (preserving the real photo instead of letting the model reinterpret it — the deliberate, correct choice for a real product image) while in Creative Product fidelity the product reference is sent to the model directly. This is the complete "write something" → "make something" path: Business Brain and Product Library assets are already real generation inputs, end to end, with existing regression coverage (M2/M3) and Founder Live QA already passed on the deployed Preview.

No further Visual Execution work was needed or added for V0.8 — building anything further here would be exactly the "large visual system" the brief said not to build blindly. If deeper visual work (new variation types, more automated composition, etc.) is ever wanted, that is new scope for a later version, not a V0.8 gap.

## Regression coverage

`scripts/qa-v05.mjs`'s frontend suite (real `index.html` inline script, mocked `fetch`/`crypto`/`confirm`) now additionally asserts, across all six engines: a fresh result starts unsaved (Save button enabled, status line says so); `saveResult()` persists it with the correct `engine`/`project`/`id` and flips the button/status to saved; reopening a saved result via `openHistory` marks it saved without a new request; a second-version regeneration from there is unsaved again; `deleteResult()` is guarded by confirmation and removes exactly the targeted entry. The existing legacy-history (pre-`project`/`id` entries), navigation-race, malformed-storage and escaped-Brain-HTML coverage is unchanged and still passes.

## Post-launch fix — workspace export/import across Preview origins

Founder Live QA blocker: opening the new `shaghil-v0.8` Preview asked the Founder to re-enter Business Brain, brand assets and the whole Product Library (Wash Me, النفسية محتاجه بحر) from scratch, even though all of it had already been populated and Founder-QA-tested on the V0.7 Preview.

**Root cause (confirmed, not a bug):** every persistence mechanism this app uses — `localStorage` (`brain`, `shaghilHistory`) and IndexedDB (`shaghil-visual-v1`: `brand`, `products`, `visuals`, `packs`) — is scoped by the browser to the page's **origin** (scheme + host + port). This was already documented in V0.7.md and DEPLOY.md ("Different Preview URLs do not share IndexedDB/localStorage") but had not yet been felt in practice. Vercel gives each branch its own Preview hostname, so `shaghil-v0.7`'s Preview and `shaghil-v0.8`'s Preview are different origins by construction; no application code change could have prevented this, and switching the underlying storage technology would not fix it either, since the same origin rule applies to every browser storage API (localStorage, IndexedDB, cookies, cache storage). The V0.7 data was never touched, deleted, or migrated — it is exactly where it was, under the V0.7 Preview's own origin, and remains reachable simply by opening that same V0.7 Preview URL again in the same browser (unless the Founder has since cleared that origin's site data, which nothing in this session did).

**Fix — local-first export/import, no new infrastructure:** a new `Workspace` module (`lib/workspace-transfer.mjs`, wired into `lib/visual-studio.mjs`, UI in the Business Brain screen) can:
- **Export** — reads `localStorage['brain']`/`['shaghilHistory']` plus every IndexedDB store (`loadBrand`, `listProducts`, `listVisuals`, `listPacks` — the same functions the app already uses) via a small recursive serializer that turns every `Blob` (product images, brand logo/references, rendered visuals) into base64 in place, and downloads the whole thing as one JSON file (`shaghil-workspace-<business>-<date>.json`). No server, no cloud storage — the file is a local download, transferred by the Founder the same way any downloaded file is.
- **Import** — reads that JSON file, reverses the same serializer back into real `Blob`s, and writes everything back through the existing `saveBrand`/`saveProduct`/`saveVisual`/`savePack` functions (so the same validation/caps already in place still apply) plus a de-duplicating merge into `shaghilHistory`. Product/visual/pack ids are preserved from the export, so `put()`-based storage makes re-importing the same file idempotent — nothing is duplicated. Business Brain is only overwritten if the destination has none yet, or the Founder confirms; nothing already present on the new origin is silently destroyed. Per-item import failures (e.g. the 12-product cap) are caught individually and reported in a plain-language summary rather than aborting the whole import.

This is intentionally a manual, Founder-triggered transfer (not an automatic sync) — it is local-first, adds no dependency and no server-side state, and directly matches how the app already treats all its other local data.

**Would a stable Preview/custom origin prevent this going forward?** Yes. Pointing a single stable custom domain (or Vercel's per-branch alias, if kept constant across future work on the same branch) at whichever Preview is "current" would mean the Founder always opens the same origin, so this specific class of interruption would not recur for continued work on one branch. It would **not**, however, remove the need for export/import in general: moving to a *different* branch/version (as this V0.7 → V0.8 transition did) is still a deliberate new origin, and only an actual production domain would unify everything long-term — which is explicitly out of scope pre-Founder-approval. Export/import is the right general-purpose answer regardless of hosting setup; a stable per-branch alias is a complementary, optional mitigation the Founder can request separately if wanted.

Added `scripts/qa-v08-workspace-transfer.mjs` (wired into `npm run qa`): two real, separate Node processes stand in for two separate browser origins (a fresh `fake-indexeddb` `IDBFactory` and a fresh `localStorage` map each) sharing nothing but the exported JSON file. It builds a fully populated Najoob workspace (Business Brain, brand logo, both named products with real image bytes, a saved visual, a campaign pack, and history) in the first, exports it, imports it into the completely empty second, and asserts everything reconstructs byte-for-byte and field-for-field — then imports the same file again and asserts nothing duplicates.

## Post-launch fix — Import control unreachable on an empty origin

Founder Live QA blocker: after successfully recovering the V0.7 workspace into a JSON file (via the DevTools console script), the Founder opened the V0.8 Preview and found no Export/Import UI anywhere — the Business Brain screen ended at "حفظ والبدء" with no way to import the recovered file.

**Root cause:** the Export/Import section had only been added to `#brain`, the Business Brain *summary* screen. `brainScreen()` only ever renders `#brain` once a Business Brain already exists (`if(!getBrain())return setup()`); on a brand-new, empty origin it always redirects straight to the empty `setup()` form instead, where no import control existed. The one screen where recovery is actually needed was exactly the one screen that didn't offer it.

**Fix:** added a **استيراد مساحة عمل محفوظة** (Import a saved workspace) block directly to the top of the empty `#setup` form, wired to the same `Workspace.import` handler — so it's reachable before a Business Brain exists, with no dependency on any prior data. Export remains on the `#brain` summary screen only (meaningful once there's something to export). Status feedback (`workspace-transfer.mjs`'s `status()`) now updates every `.workspaceStatus` element rather than one fixed id, since the control now exists on two screens; a successful import that restores a Business Brain now navigates straight to Home (via `home()`) regardless of which screen it was triggered from, rather than leaving the Founder on a now-stale empty form.

Added `scripts/qa-v08-import-recovery-ui.mjs` (wired into `npm run qa`, its own process for a clean origin): drives the real `setup()`/`home()`/`Products`/`Workspace` code on a genuinely empty origin, confirms the import control is visible on that empty screen, imports a recovered Najoob workspace (Business Brain, both named products with real image bytes, history), confirms Business Brain/products/history are all restored and the app lands on Home, confirms the restored library renders through the real Product Library UI, and confirms everything survives a simulated reload. Verified this test fails against the pre-fix markup with the exact assertion matching the reported symptom, and passes with the fix.
